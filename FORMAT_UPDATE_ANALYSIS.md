# Разбор доработки выбора формата

Дата разбора: 10 сентября 2026 года.

## Короткий вывод

Основная идея задачи понятна. Текущий плоский `select` с 28 форматами нужно заменить на иерархический выбор, в котором пользователь сначала выбирает тип материала (`Обычный` или `UGC`), затем — рубрику, а затем — конечный формат. Для обычных материалов отдельного уровня рубрик в макете нет: после выбора типа сразу показываются восемь конечных форматов. Для UGC показываются семь рубрик, а затем подтипы выбранной рубрики.

Это изменение затрагивает не только внешний вид кнопки. Оно добавляет промежуточное состояние навигации по каталогу форматов, меняет семантику контролов и добавляет отдельный мобильный сценарий. При этом текущую бизнес-логику смены пресета, сброса отметок, подтверждения и сохранения в `localStorage` можно сохранить.

Продуктовые решения по основным блокерам подтверждены. На мобильном новый выбор будет открываться в модальном окне; десктопный выбор останется в сайдбаре. Шапка не управляет ветками, а только отражает уже выбранный конечный формат. UGC дополнительно маркируется жёлтым бейджем, а повторяющийся суффикс `(UGC)` убирается из названий.

Открытым остаётся только визуальное решение для кнопок рубрик. Ниже зафиксирована рекомендуемая схема, которая опирается на уже существующую навигацию приложения и не создаёт отдельную мини-дизайн-систему внутри сайдбара.

## Что показано в макете

Макет предлагает следующий сценарий:

1. В верхнем уровне блока «Формат» находятся две сегментированные кнопки:
   - `Обычный` с числом `8`;
   - `UGC` с числом `20`.
2. При выборе `Обычный` ниже видны восемь конечных форматов в виде вертикальных кнопок.
3. При выборе `UGC` ниже появляются чипы рубрик с количеством форматов в каждой рубрике.
4. Под рубриками показываются только подтипы выбранной рубрики.
5. Текущий конечный формат выделен светло-жёлтым фоном, жёлтой рамкой, полужирным текстом и галочкой справа.
6. Нажатие верхнего типа или UGC-рубрики само по себе не меняет чек-лист: оно только открывает соответствующую ветку. Чек-лист меняется после нажатия конечного формата.
7. После выбора конечного формата обновляются заголовок, набор пунктов, разделы и общий прогресс.

Жёлтый бейдж `UGC` рядом с заголовком активного UGC-формата входит в задачу. Суффикс `(UGC)` в названиях форматов нужно убрать: тип уже понятен по открытой ветке и бейджу, а повтор создаёт лишний визуальный шум.

## Как это соотносится с текущей реализацией

Сейчас:

- `src/components/FormatControl.jsx` рендерит один нативный `select` из всех значений `PRESET_LABELS`;
- `src/components/ChecklistWorkspace.jsx` размещает один экземпляр контрола в десктопном сайдбаре и второй — в мобильной шапке;
- при смене конечного пресета вызывается `switchPreset` из `src/App.jsx`;
- если уже есть выполненные пункты, перед сменой показывается `ConfirmationDialog`;
- подтверждённая смена пресета сбрасывает отметки и свёрнутые разделы, выключает режим фокуса, прокручивает интерфейс к началу и показывает уведомление;
- выбранный ключ пресета сохраняется в `localStorage` под ключом `preset`;
- полный reset возвращает `default`.

Эти инварианты стоит сохранить. Новые верхние уровни должны быть навигацией внутри селектора, а не новыми пресетами.

## Предлагаемая модель поведения

### Разница между открытой веткой и выбранным форматом

У компонента появятся два разных понятия:

- `preset` — реально выбранный конечный формат, уже существующее состояние приложения;
- открытая ветка — локальное UI-состояние контрола: `Обычный`/`UGC` и, для UGC, текущая рубрика.

Нажатие типа или рубрики меняет только открытую ветку. Нажатие конечного формата запускает существующий сценарий `changePreset` / `switchPreset`.

При первом рендере открытую ветку лучше вычислять из сохранённого `preset`. Например, для `ugc18` автоматически открыть `UGC` → `Итоги сообщества`, а для `invest` — `Обычный`.

### Смена формата и подтверждение

Рекомендуемое поведение:

- если нет выполненных пунктов, конечный формат применяется сразу;
- если выполненные пункты есть, показывается существующее подтверждение;
- верхний тип и рубрика никогда не вызывают подтверждение и не сбрасывают данные;
- при отмене подтверждения активный `preset` не меняется;
- фокус после отмены возвращается на кнопку конечного формата, с которой открыли диалог;
- после подтверждения открытая ветка синхронизируется с новым `preset`.

Текущая реализация ищет видимый `select` через два ref. После перехода на кнопки проще сохранять `event.currentTarget` конечной кнопки как источник действия.

### Подписи

Для UGC стоит использовать два уровня подписи, но нигде не повторять суффикс `(UGC)`:

- контекстная подпись — для заголовка, уведомления и диалога, например `Вопрос—ответ: Медицина`;
- короткая подпись — внутри уже открытой рубрики, например `Медицина`.

Это рекомендуемый вариант: в рубрике пользователь уже видит контекст `Вопрос—ответ`, поэтому его повтор в каждой строке только удлиняет список. В шапке и подтверждении рубрика не видна, поэтому там полезна контекстная подпись. Единая короткая подпись во всех местах проще технически, но фразы вроде `Чек-лист проверки · Ответ` или `Новый формат: «Подборка»` будут недостаточно самостоятельными.

### Счётчики

Числа `8`, `20` и числа у UGC-рубрик выглядят как количество доступных конечных форматов, а не количество пунктов чек-листа. Их лучше вычислять из конфигурации групп, а не хранить отдельными константами, чтобы они не расходились при добавлении новых пресетов.

## Предлагаемая техническая структура

Без изменения ключей существующих пресетов можно добавить рядом с `PRESET_LABELS` декларативную конфигурацию групп, например:

```js
export const FORMAT_GROUPS = [
  {
    id: "regular",
    label: "Обычный",
    items: ["default", "invest", "shopping", "tests", "compare", "spending", "cd", "shorts"],
  },
  {
    id: "ugc",
    label: "UGC",
    categories: [
      { id: "base", label: "Базовый", items: ["ugc"] },
      { id: "hate", label: "Бесит", items: ["ugc3", "ugc4"] },
      // остальные рубрики
    ],
  },
];
```

Точные короткие подписи можно хранить в этой конфигурации либо в отдельном `PRESET_SHORT_LABELS`. Не стоит выводить рубрики из строк в `PRESET_LABELS`: названия являются пользовательским текстом и могут меняться.

Ожидаемые зоны изменения:

- `src/checklist-data.js` — таксономия групп и короткие подписи;
- `src/components/FormatControl.jsx` — новый иерархический интерфейс и локальное состояние открытой ветки;
- `src/components/ChecklistWorkspace.jsx` — передача обработчика конечного выбора и восстановление фокуса для подтверждения;
- `src/App.css` — сегментированный переключатель, чипы, строки подтипов, состояния hover/focus/selected, тёмная тема и адаптив;
- при необходимости `src/components/ConfirmationDialog.jsx` — только если изменится текст или политика подтверждения.

Менять `getPresetData`, ключи пресетов и формат значения `localStorage.preset` не требуется. Если меняется только представление выбора, увеличивать `DATA_VERSION` также не нужно: версия сейчас относится к содержимому чек-листа и сохранённым отметкам.

## Адаптив и компоновка

### Десктоп

Макет хорошо ложится в существующий сайдбар шириной 280 px. Сайдбар уже sticky и имеет собственный вертикальный скролл, поэтому разросшийся блок выбора не должен обрезать навигацию и прогресс. Нужно проверить самое высокое состояние: восемь обычных форматов и UGC-рубрику `Вопрос—ответ` с шестью подтипами.

### Мобильная версия — принятое решение

Сейчас нативный select находится в sticky-шапке. Вся иерархия в шапке сделала бы её слишком высокой, поэтому для мобильной версии подтверждён отдельный модальный сценарий:

1. В шапке оставить компактную кнопку с текущим полным или сокращённым названием формата.
2. По нажатию открывать модальное окно с той же иерархией `тип → рубрика → подтип`.
3. После выбора конечного формата закрывать окно, если не требуется подтверждение.
4. Если требуется подтверждение, передавать фокус в диалог подтверждения; при отмене оставлять действующий формат и открытую пользователем рубрику.

Команда отдельно уточнит востребованность мобильной версии. До этого модалку можно считать целевым поведением, но сложные мобильные улучшения и анимации не должны увеличивать первый объём работ без подтверждённой пользы.

## Рекомендация по дизайну кнопок рубрик

### Почему текущий вариант макета ощущается спорным

Пунктирные овальные чипы уже используются в приложении для контентных фильтров. Такая форма сообщает «необязательный фильтр, который можно включить или выключить». Рубрика работает иначе: это обязательный уровень навигации, у которого в каждый момент открыто одно значение. Из-за этого одинаковый паттерн создаёт неверное ожидание и визуально конкурирует с настоящими фильтрами справа.

Дополнительные проблемы макета:

- разная ширина чипов создаёт рваный край и затрудняет быстрое сканирование;
- пунктирная рамка выглядит как disabled или незавершённое состояние;
- активная чёрная рубрика слишком похожа на активный тип `UGC`, хотя это разные уровни;
- жёлтая строка выбранного подтипа и чёрная рубрика одновременно претендуют на главный акцент.

### Рекомендуемый вариант: компактный навигационный список

Рубрики лучше оформить по образцу существующего `.section-nav`:

- одна рубрика на строку, ширина 100%;
- высота строки около 34–36 px и радиус 7 px из текущей системы;
- название слева, количество форматов справа моноширинным шрифтом;
- обычное состояние без рамки и без отдельного фона;
- hover — `var(--surface-soft)`;
- открытая рубрика — `var(--surface-soft)`, полужирный текст и акцентная жёлтая полоска слева;
- выбранный конечный формат ниже остаётся отдельной строкой с жёлтой рамкой/фоном и галочкой.

Так уровни получают разный визуальный язык:

- `Обычный / UGC` — сегментированный переключатель типа;
- рубрики — навигационный список;
- подтипы — конечный выбор с явной отметкой выбранного значения.

Плюсы: полностью совпадает с текущими токенами и паттернами, хорошо работает в светлой и тёмной теме, даёт крупную область нажатия и не требует новых декоративных правил. Минус: семь рубрик занимают больше высоты, но сайдбар уже прокручивается, а ясность здесь важнее экономии примерно одной строки.

### Компактная альтернатива

Если вертикальная высота окажется критична, можно оставить переносимые чипы, но сделать их не овальными и не пунктирными:

- радиус 7–8 px;
- сплошная прозрачная рамка в normal-состоянии;
- `var(--surface-soft)` на hover;
- активная рубрика с мягким фоном и жёлтой нижней или левой отметкой;
- без чёрной заливки, чтобы активная рубрика не спорила с переключателем типа.

Этот вариант компактнее, но хуже сканируется и менее явно показывает, что рубрики взаимоисключающие. Поэтому основной рекомендацией остаётся список.

## Доступность и клавиатура

Нативный `select` сейчас доступен с клавиатуры и хорошо объявляется скринридером. После замены это качество нужно сохранить явно:

- все интерактивные элементы должны быть `button`, а не кликабельными `div`;
- выбранный тип, рубрика и конечный формат должны иметь машинно читаемое состояние (`aria-pressed`, `aria-current` либо корректно собранные radio/tab-группы);
- визуальная галочка не должна быть единственным признаком выбора;
- у двух кнопок с текстом `Обычный` должны быть разные доступные имена, например `Тип: Обычный` и `Формат: Обычный`;
- должен быть заметный `:focus-visible` в светлой и тёмной темах;
- Enter и Space должны активировать контролы; если выбирается семантика tabs/radio, желательно поддержать стрелки;
- счётчики лучше скрыть от скринридера или озвучивать осмысленно: `UGC, 20 форматов`;
- при подтверждении смены формата сохранить существующую фокус-ловушку и возврат фокуса.

## Что не должно измениться без отдельного требования

- состав чек-листов и правила `getPresetData`;
- ключи пресетов и совместимость с сохранённым `preset`;
- сброс отметок при подтверждённой смене формата;
- сохранение темы, фильтров и заметок;
- поведение полного reset;
- прогресс и навигация по разделам;
- структура шапки, кроме согласованного UGC-бейджа и удаления `(UGC)` из названия;
- общий визуальный стиль остальных частей приложения.

## Критерии приёмки

1. Все существующие 28 форматов доступны из нового контрола ровно по одному разу.
2. Обычная ветка содержит 8 форматов, UGC — 20; количества рубрик совпадают с таблицей выше.
3. При загрузке открыта ветка сохранённого конечного пресета, и выбранная строка отмечена визуально и семантически.
4. Переключение только типа или рубрики не меняет чек-лист, прогресс и `localStorage.preset`.
5. Нажатие конечного формата без выполненных пунктов сразу применяет формат.
6. При наличии выполненных пунктов конечный выбор показывает подтверждение; отмена ничего не сбрасывает, подтверждение сохраняет текущую политику сброса.
7. Заголовок, состав пунктов, прогресс и toast соответствуют выбранному конечному формату.
8. Полный reset возвращает `Обычный` (`default`) и синхронизирует открытую ветку.
9. Контрол корректно работает мышью, с клавиатуры и со скринридером.
10. Светлая и тёмная темы имеют читаемые normal, hover, focus и selected-состояния.
11. Десктопный сайдбар не обрезает длинные подписи и остаётся прокручиваемым на небольшой высоте окна.
12. Мобильный сценарий не создаёт горизонтальный скролл страницы и не перекрывает основное содержимое чрезмерно высокой sticky-шапкой.
13. Существующие сохранённые значения `preset` продолжают открываться без миграции.
14. У UGC-формата в шапке показан жёлтый бейдж `UGC`, при этом `(UGC)` не повторяется в названиях селектора, заголовка, toast и подтверждения.
15. При отмене подтверждения остаётся прежний выбранный формат, кнопка неподтверждённого формата возвращается в обычное состояние, а открытая UGC-рубрика не закрывается.
16. Проходят `npm run format:check`, `npm run lint` и `npm run build`.

## Зафиксированные решения

1. На мобильном выбор открывается в модальном окне. Востребованность мобильной версии команда уточнит отдельно.
2. Шапка только отражает уже выбранный конечный формат; её общая структура остаётся прежней.
3. Тип и рубрика являются навигацией внутри контрола. Реальная смена чек-листа происходит только по конечному формату.
4. Если подтверждение отменено, действующий формат сохраняется. Кнопка неподтверждённого варианта сбрасывается, но открытая рубрика, например `Вопрос—ответ`, остаётся на экране.
5. Жёлтый бейдж `UGC` входит в задачу.
6. Суффикс `(UGC)` удаляется из пользовательских названий.
7. Короткие названия используются внутри открытой рубрики; в шапке и служебных сообщениях остаётся самостоятельная контекстная подпись без `(UGC)`.
8. Счётчики форматов показываются и вычисляются из конфигурации.
9. Поведение смены формата и подтверждения сохраняет текущие правила сброса.
10. Все состояния строятся на текущих CSS-переменных и паттернах светлой/тёмной темы.
11. Анимация переключения веток остаётся в бэклоге.

## Выбранное оформление рубрик

Для рубрик принят полноширинный навигационный список: название слева, счётчик справа, мягкий фон у открытой строки и жёлтая акцентная полоска. Компактные прямоугольные чипы не используются.

## Оценка ясности задачи

Логика, состав форматов, мобильный сценарий, подтверждение, правила подписей и оформление рубрик определены достаточно для реализации.

Дополнительного изменения модели данных и миграции пользовательского состояния не потребуется; основная сложность будет сосредоточена в компоненте выбора, мобильной модалке и доступности.
